🛡️ Publicació BULLETPROOF de MediCar Plus

Sistema de 10 capes que garanteix que MAI es publiqui un .exe corrupte als clients, i que si passés, tinguis una palanca d'emergència remota per bloquejar-lo al moment.

👉 UNA SOLA COMANDA
cd C:\Users\...\medicarplus-electron
powershell -File publish-safe.ps1

Això fa TOT: sync → validate → bump → build → smoke → publish. Aborta a la primera cosa rara.

🆘 URGÈNCIA: si algun cop publiques una versió dolenta i vols aturar-la globalment, crea/edita /app/backend/electron_channel.json amb la versió al camp blocked_versions i tots els clients pararan de descarregar-la immediatament.

🧬 Les 7 capes de defensa

Capa 1 — Manifest servidor (SHA-256)
El backend serveix /api/electron/manifest amb el hash SHA-256 i mida de cada fitxer font. Aquest és l'origen de veritat. Sense això, no es descarrega res.
Capa 2 — sync.js atòmic amb verificació SHA
Baixa cada fitxer a .sync-tmp/, verifica SHA-256 contra el manifest, verifica signatures de contingut, i només llavors sobreescriu. Si algun falla, els fitxers locals no es toquen. Amb backup automàtic.
Capa 3 — validate-local.js pre-build
Abans d'obrir electron-builder, un script inspecciona els fitxers locals i verifica que continguin les strings crítiques (MediCar Plus, Entradas del día, require('electron'), autoUpdater, etc.). Si en falta una: abort exit 3.
Capa 4 — Client-side crash guard
Al top de index.html hi ha un boot-guard: si en 8 segons no s'ha renderitzat cap element clau, mostra una UI de recuperació al client dient-li que reinstal·li. Cap client veurà mai una finestra en blanc.
Capa 5 — smoke-test.js post-build
Després de compilar el .exe, un altre script obre l'app.asar compilat i verifica que dins hi són les strings crítiques + que els installers tenen mida raonable (>30 MB). Si falla: no es publica.
Capa 6 — publish-safe.ps1 orquestrador
Un únic script PowerShell que encadena tot amb ✅/❌ clars i $ErrorActionPreference = "Stop". Impossible saltar-se cap pas.
Capa 7 — Verificació post-release
Consulta l'API de GitHub per confirmar que la release apareix realment amb la versió esperada (via api.github.com/.../releases/latest).
Capa 8 — KILL SWITCH remot (control total)
Endpoint /api/electron/update-channel. Els clients el consulten ABANS d'auto-actualitzar-se. Pots bloquejar QUALSEVOL versió des del servidor editant /app/backend/electron_channel.json: 
{
  "latest_safe_version": "2.0.21",
  "blocked_versions": ["2.0.19", "2.0.20"],
  "message": "Actualitza a l'última versió"
}
Efecte immediat en tots els clients: no descarregaran versions bloquejades.
Capa 9 — Main.js consulta el kill switch
Al detectar una nova versió, el client Electron truca al servidor. Si el servidor diu "aquesta versió està bloquejada", cancel·la la descàrrega/instal·lació. Palanca d'emergència sense necessitat de tocar res al client.
Capa 10 — Boot guard + window.onerror global
Dins index.html: si al arrencar (a) es llença qualsevol error JS o (b) no es renderitza cap element principal en 10 segons, mostra UI de recuperació amb enllaç a reinstalar. Cap client veurà una finestra en blanc mai.

🚨 Què passa si alguna capa falla?

Capa 1 (manifest) falla → sync continua amb signatures de contingut (menys estricte però igual detecta HTML 404).
Capa 2 (sync) falla per un fitxer → mantenim la còpia local d'aquell fitxer i seguim. La build continuarà només si el local és vàlid.
Capa 3 (validate) falla → ABORT total. Missatge dient exactament què falta. Solució: npm run sync i tornar a intentar.
Capa 5 (smoke) falla → ABORT abans de publish. El .exe no arriba mai a GitHub. Els clients no s'assabenten.
Client rep una versió corrupta miraculosament → Capa 4 (crash guard) mostra pantalla de recuperació amb enllaç a reinstalar. No finestres en blanc.
